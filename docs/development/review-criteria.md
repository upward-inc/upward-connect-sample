# コードレビュー基準

コードレビュー時に確認すべき基準を定義する。

## 前提

- 差分に含まれる全言語（TypeScript, YAML 等）を対象とする
- 言語固有のベストプラクティス違反も指摘対象とする

## 観点

### 1. セキュリティ

- 認証・認可フローの完全性（JWT 検証、トークン管理、署名検証）
- 入力バリデーションの漏れ（ユーザー入力、外部データ）
- シークレットのハードコード・ログ出力
- OWASP Top 10 に該当するパターン（インジェクション、SSRF 等）

### 2. 仕様準拠

- 使用しているプロトコルやライブラリの仕様に沿った実装か（例: OAuth 2.0 / OIDC の RFC 準拠）
- エラーコード、パラメータ名等が規約に一致しているか

### 3. エラーハンドリング

- 外部 API 呼び出しの未キャッチ例外
- ユーザー向けのエラーレスポンスが適切か（500 ではなく 4xx を返すべき箇所）
- エラー時のリソースリーク（DB コネクション、ファイルハンドル等）

### 4. パフォーマンス

- N+1 クエリ、不要なループ内 API 呼び出し
- 不要な再レンダリングや重い処理のメインスレッド実行
- 大量データ処理時のメモリ効率（不要な全件ロード等）

### 5. 破壊的変更

- API の後方互換性（エンドポイント、レスポンス構造の変更）
- DB スキーマ変更の安全性（既存データへの影響、マイグレーション手順）
- 公開インターフェースの変更が利用側に影響しないか

### 6. テスト

- 新規機能・バグ修正に対応するテストが追加されているか
- 既存テストが変更に追従しているか（壊れたまま放置されていないか）

### 7. コード品質

- 冗長なコード、コピー&ペーストによる重複
- 不要なデバッグコード（console.log 等）の残存
- 回帰バグ（以前追加した修正が意図せず除去されていないか）
- 命名の明確さ（意図が伝わる変数名・関数名か）

### 8. 整合性

- 変更箇所と類似のパターンを持つ未変更コードに、同様の修正漏れがないか
- 命名・構造・エラー処理の方針が既存コードと一貫しているか
- 変更により、未変更箇所の前提（引数、戻り値、型定義等）が崩れていないか
- 既存の共通ユーティリティやヘルパーで代替できる処理を独自に再実装していないか

### 9. 依存関係

- 新規パッケージのライセンスがプロジェクトと互換性があるか
- メンテナンスが活発か（アーカイブ済み、長期間更新なし等）
- バンドルサイズへの影響が妥当か

### 10. ドキュメント整合性

- 実装を変更したとき、その実装を説明するドキュメント（`docs/` 配下・`CLAUDE.md` 等）があれば同一 PR で更新したか。設計が廃止された場合は該当節を削除したか、将来構想として現状の記述と分離したか
- 変更が既存文書の記述（型名・エンドポイント・定数値・永続化方式等）を陳腐化させていないか。陳腐化していれば「ドキュメントの更新漏れ」または「廃止された設計の残存」として指摘する

文書自体の書き方（意図・不変条件を書き、揮発的な具体はコード・テストを参照する等）は `.claude/rules/documentation.md` に従う。
