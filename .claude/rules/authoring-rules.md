# ルールファイルの書き方

`.claude/rules/` 配下の各ルールファイルに何を書き、何を書かないかを定める。ルールについてのルール。

本ルールを適用する際は `writing-style.md` も併せて読むこと。改行・句読点・借用語等の散文スタイルはそちらの規則に従う。

## 基本方針

**ルールファイルには、遵守を判定でき、レビューで根拠として参照できる「こうせよ」のみを置く。**

機序の解説・実装手順・長い NG/OK walkthrough・ヘルパーの所在カタログといった how-to は skill に置き、ルールからは参照に留める。

ただし規約の遵守形を一目で示す短いコード例はルールに残してよい。skill へ出すのは長い walkthrough と機序解説のコードであり、数行の例示まで排除する趣旨ではない。

## 規約と how-to の仕分け軸

「テクニックか」ではなく「レビュー指摘の対象になる規約か」で切る。

- ルールに置く (規約): 違反/遵守を客観的に判定でき、PR レビューで「このルールに反する」と参照できる「こうせよ」
- skill に置く (how-to): なぜそうするかの機序、実装手順、長い NG/OK walkthrough、所在カタログなど、判定対象ではなく背景・作業支援にあたるもの

判断に迷う場合は「この記述に違反しているかどうかをレビューで指摘できるか?」で考える。指摘できるなら規約、できないなら how-to。

### 閾値ヒューリスティックは規約側に残す

`test.each` は 3 件以上で集約する、boilerplate は 5 ファイル以上で共通化する、のような数値閾値は遵守判定のトリガになるためルール側に置く。閾値の背景・例外の議論は skill に置いてよい。

## 構造

- 各ルールは命令形 (断定・「〜すること」) で書く。判定可能な形にする。
- how-to を skill へ移したセクションは、ルール側に「背景と実コードは `{skill 名}` スキルを参照」のような相互参照を 1 行添える。
- frontmatter の `paths:` は、そのルールが適用されるファイルパスを過不足なく列挙する。

## チェック観点

レビュー時・記述時に以下を自問する:

- この記述は遵守/違反をレビューで指摘できるか? できないなら how-to であり skill 側に置くべきではないか?
- 機序の長い解説・長い NG/OK walkthrough・カタログがルール内に残っていないか? (規約の遵守形を示す短い例は残してよい)
- 閾値などの判定トリガはルール側に残っているか?
