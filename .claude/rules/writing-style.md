# 文章スタイルルール

コメント・JSDoc・Markdown ドキュメント・コミットメッセージ等、プロジェクト内で記述するすべての散文に適用する。

## 適用対象

frontmatter の `paths` でマッチするファイル内の散文に適用する。

- Markdown ドキュメント (`.md`, `.mdx`, `README`, `docs/` 配下 等)
- YAML / JSON with Comments (`.yml`, `.yaml`, `.jsonc`, `.json5`) のコメント (`#` / `//` / `/* */`) — CI/CD ワークフロー、OpenAPI spec、エディタ・ツール設定等の説明文
- JS/TS ソース: インラインコメント (`//`)、ブロックコメント (`/* */`)、JSDoc / TSDoc
- その他、ファイル内に記述する人間向けの自由記述テキスト

対象外:

- 識別子 (変数名、関数名、ファイル名等)
- データ構造内の文字列リテラル (i18n 翻訳、UI 文言等、別途専用のガイドがあるもの)
- コミットメッセージ・PR description 等のファイル外テキスト (ルールを自動参照できないため対象外。守るべき精神は同じだが、人手で適用する必要がある)

## 改行規則

### 基本方針

**文の途中で改行を入れない。改行は意味の切れ目でのみ行う。**

日本語・英語いずれの散文にも適用する。原則は共通で、区切り記号が言語ごとに異なるだけ。

### 改行してよいポイント

優先順位の高い順に並べる。上位で改行できるならそれを使い、下位はあくまで代替手段。

1. **文末記号の直後 (最優先)**
   - 日本語: 句点「。」
   - 英語: `.` / `!` / `?`
2. **段落の区切り (空行)**
3. **箇条書き・リストの項目区切り**
4. **Markdown の見出し、コードブロック、引用ブロックの前後**
5. **節の切れ目 (最終手段)**
   - 日本語: 読点「、」
   - 英語: `,` / `;` / `:` / `—`
   - **使える条件 (両方を満たすとき):**
     1. 句点 (「。」/ `.`) で文を分けると文意が壊れる・冗長になる (例: 条件節・関係節で一体の意味を成すとき)
     2. 一文が長すぎる (目安: 日本語 80 文字超 / 英語 100 文字超)
   - この条件を満たさないときは、節区切り改行ではなく「文自体を句点で分割する」ことを検討する

### 改行してはいけないポイント

- 単語・数値・識別子の途中
- 一文の中ほどで「読みやすくするため」と称して入れる改行
- 日本語: 助詞 (「が」「を」「に」「は」「の」「で」「と」等) の直前・直後で文を途切れさせる
- 英語: 冠詞・前置詞・接続詞 (`the` / `a` / `of` / `in` / `and` / `to` 等) の直前・直後で文を途切れさせる
- 英語: 固有名詞や慣用句・熟語の途中 (例: "New York", "as well as", "in order to")

### 理由

- 文の途中での改行は語順の把握を阻害し、かえって読みにくくする
- Markdown / JSDoc ビューア・IDE のコメント表示は自動折り返しするため、手動改行は表示幅に合わない (狭い画面では二重に折り返され、広い画面では不自然に短い行になる)
- 1 文字の修正で複数行の diff が発生し、レビュー時のノイズになる
- 検索 (grep) で文の一部がマッチしなくなる

## 借用語 (英単語・カタカナ語) の扱い

### 基本方針

**英単語を日本語の散文に混ぜるのは、日本語開発の現場で借用語として定着している語に限る。定着していない英単語は日本語に訳す。**

技術用語・識別子・API 名などを英語のまま書くのは自然なので禁じない。
問題になるのは、英語で思考した一般語を訳さずそのまま動詞化・形容詞化するケース。

### 判定軸

「日本語話者がこの語を普段カタカナ/英語のまま会話・ドキュメントで使うか?」を基準に判断する。

**そのまま使ってよい:**

- 定着した借用語: `fetch` `deploy` `build` `commit` `embed` `merge` など、技術文脈の定番語
- 定着した技術略語: `TDD` `API` `CI` など、日本語話者がそのまま発音・使用する略語

**訳す:**

- 未定着の一般英単語: `cite` → 引用 / 参照、`leverage` → 活用、`surface` → 表に出す、など

**初出で訳を添える:**

- フルスペルが読者に自明でない略語: `SSOT`（唯一の情報源）、`BFF`（Backend for Frontend）、など
  - 初出時のみ括弧内に日本語訳やフルスペルを添え、以降は略語のみでよい

### 理由

英語で考えてから日本語を書くと、定着していない一般英単語を訳さず `cite できる` のように写してしまいやすい。
読み手に余計な変換コストを強い、文の調子も不自然になる。

### 例

NG (未定着の英単語を動詞化):

```markdown
レビューで cite できる規約のみを置く。
```

OK (日本語に訳す):

```markdown
レビューで根拠として参照できる規約のみを置く。
```

## 例

### 例 1: JSDoc の文中改行

NG:

```ts
/**
 * ユーザーが管理者権限を持っているかどうかを
 * 判定する。
 */
function isAdmin(user: User): boolean { ... }
```

OK:

```ts
/**
 * ユーザーが管理者権限を持っているかどうかを判定する。
 */
function isAdmin(user: User): boolean { ... }
```

### 例 2: 長文の JSDoc

NG (読点の途中で折り返す):

```ts
/**
 * ユーザーが管理者権限を持っているかどうかを判定する。権限情報は
 * キャッシュされているため、最新状態が必要な場合は refresh を呼ぶこと。
 */
```

OK (句点で文を分けて改行する):

```ts
/**
 * ユーザーが管理者権限を持っているかどうかを判定する。
 * 権限情報はキャッシュされているため、最新状態が必要な場合は refresh を呼ぶこと。
 */
```

### 例 3: Markdown の段落

NG:

```markdown
この機能はスケジュールの取得を
日単位から bucket 単位に変更し、
キャッシュヒット率を改善する。
```

OK (一文を折り返さずに一行で書く):

```markdown
この機能はスケジュールの取得を日単位から bucket 単位に変更し、キャッシュヒット率を改善する。
```

OK (句点で分割):

```markdown
この機能はスケジュールの取得を日単位から bucket 単位に変更する。
これによりキャッシュヒット率が改善する。
```

### 例 4: 英語コメント

NG (冠詞の前で改行):

```ts
/**
 * Returns true when the user has
 * administrator privileges.
 */
```

OK:

```ts
/**
 * Returns true when the user has administrator privileges.
 */
```

### 例 5: 英語の長文

NG (前置詞 `in` の前で折り返す):

```markdown
This feature changes schedule fetching from day-based to bucket-based in
order to improve cache hit rate.
```

OK (ピリオドで文を分ける):

```markdown
This feature changes schedule fetching from day-based to bucket-based.
It improves cache hit rate.
```

## チェック観点

レビュー時・記述時に以下を自問する:

- 改行箇所は文末記号 (「。」/ `.` `!` `?`) か節区切り (「、」/ `,` `;` `:`) の直後か、段落区切りか?
- 違う場合、なぜそこで改行したのか説明できるか?
- 説明できないなら、その改行は不要。削除する。
- 英単語を混ぜた箇所は、日本語話者が普段そのまま使う定着語か? 未定着の一般語なら訳したか?
