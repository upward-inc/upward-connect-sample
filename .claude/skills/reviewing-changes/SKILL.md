# 変更内容のレビュー

レビュー対象をサブエージェントでレビューし、問題点を報告する。

サブエージェントはセッションのコンテキストを持たないため、実装時の思い込みに囚われず客観的に問題を検出できる。

レビュー観点は `docs/development/review-criteria.md` に定義されている。必ず参照すること。

## 前提条件

- PR レビューの場合: [GitHub CLI](https://cli.github.com/) がインストール・認証済みであること

## 対象の判定

引数 `$ARGUMENTS` から対象の種別を判定する（取得方法は「対象別の取得方法」を参照）。

| 引数パターン                          | 例                                                | 対象種別                                       |
| ------------------------------------- | ------------------------------------------------- | ---------------------------------------------- |
| 数字のみ／`#` プレフィックス付き      | `123`, `#123`                                     | **PR**                                         |
| `https://` で始まる URL               | `https://github.com/owner/repo/pull/123`          | **PR**                                         |
| ローカルに存在するパス                | `apps/backend/src/routes/`, `src/foo.ts` | **ファイル・ディレクトリ**                     |
| ローカル/リモートに実在するブランチ名 | `uc-123`, `feature/x`                             | **ローカルブランチの差分（指定ブランチ）**     |
| 実在しないブランチ名／パス            | `typo-branch`                                     | **引数誤りとして確認（フォールバックしない）** |
| 引数なし                              | （なし）                                          | **ローカルブランチの差分（現在ブランチ）**     |

引数がパス・ブランチ名のいずれとしても実在しない場合は、黙って現在ブランチにフォールバックせず、引数が誤っている可能性を報告して確認する。

## 実行フロー

対象の種別によらず、以下の共通フローで実行する。差分（取得方法）の違いは「対象別の取得方法」に定義する。

### 共通フロー

1. 「対象の判定」で決定した種別に応じて、**対象のコード**を取得する（詳細は「対象別の取得方法」参照）
2. 対象ファイル一覧から、**適用すべき `.claude/rules/` 配下のルールファイル**を列挙する（詳細は「適用ルールファイルの特定」参照）
3. サブエージェントに以下を渡してレビューを依頼する
   - レビュー対象の種別（PR差分 / ブランチ差分 / ファイル・ディレクトリ）
   - 対象のコード（差分または全文）
   - 対象ファイル一覧
   - レビュー範囲（下記「レビュー範囲」参照）
   - **レビュー観点ファイル**: `docs/development/review-criteria.md` のパス。サブエージェントはこれを自身で Read し、観点に沿って指摘すること
   - **適用ルールファイル**: 2. で列挙した `.claude/rules/` 配下のパス一覧。サブエージェントはこれらを自身で Read し、ルールに沿って指摘すること、指摘の根拠として該当ルールのパスを引用することを明示的に指示する
   - `./report-format.md` の報告フォーマット
4. レビュー結果をユーザーに報告する（具体例は `./report-format.md` を参照）

> [!NOTE]
> Agent tool（サブエージェント起動）が利用できない環境では、フォールバックとしてメインエージェント自身が 3. のレビューを実行する。
> その場合も、2. で列挙したルールファイルを Read したうえで指摘する。
>
> Agent tool 利用可否の判定は「利用可能なツール一覧に Agent（または Task）が含まれているか」を直接確認すること。
> `ToolSearch` の deferred 一覧に含まれる場合は `select:Agent` 等でロードしてから利用する。
>
> フォールバック実行時は、3. で本来サブエージェントに渡す情報を一旦箇条書きで整理してから指摘を書き出すと、条件漏れが防げる。

### 対象別の取得方法

共通フロー 1. で取得する内容は対象によって異なる。

#### PR を対象とする場合（PR番号・URL）

- `PAGER=cat gh pr view {対象}` で PR のタイトル・説明・状態を取得
- `PAGER=cat gh pr diff {対象}` で差分を取得
- PR ブランチの**最新状態**がメイン作業ツリーにチェックアウトされている状態にする
  - `gh pr checkout {対象}` を実行する。既に PR ブランチに居る場合もリモートから最新化されるため常に安全に実行できる
  - 未コミット変更がある場合は事前に `git stash` する。レビュー完了後、別ブランチから切り替えた場合は元に戻し、必要に応じて `git stash pop` で復元する
  - プロジェクト外の worktree（`/tmp/` 等）は使わない（`.claude/rules/` の glob マッチがプロジェクトルート起点のため）
- `PAGER=cat gh pr view {対象} --json files --jq '.files[].path'` で変更ファイル一覧を取得
- 変更された各ファイルを Read ツールで全文取得する（大規模差分時の扱いは「大規模差分時の Read 方針」参照）

#### ローカルブランチの差分を対象とする場合（引数なし／ブランチ名指定）

- レビュー対象ブランチを確定する。引数でブランチ名が指定されていればそれを、なければ現在ブランチ（`HEAD`）を対象とする。以降 `<target>` と表記する。
- **着手前の検証（対象なし・取り違えの検出）**
  - 引数でブランチ名を指定された場合は `git rev-parse --verify <target>` で実在を確認する。実在しなければ着手せず、引数が誤っている可能性を報告して確認する。
  - `git fetch origin develop` でリモートの最新を取得する。
  - `git diff --quiet origin/develop...<target>` で差分の有無を確認する。差分が空、または `git branch --merged origin/develop` に `<target>` が含まれる（develop にマージ済み）場合は、レビューを実行せず「レビュー対象なし（差分が空／develop にマージ済み）」と報告する。
  - `<target>` が現在の作業ブランチや進行中タスクと食い違う場合は、着手前にその不一致を明示して確認する。
- `git log --oneline origin/develop..<target>` で差分コミットを確認
- `git diff origin/develop...<target>` で差分を取得
- `git diff --name-only origin/develop...<target>` で変更ファイル一覧を取得
- 変更された各ファイルを Read ツールで全文取得する（大規模差分時の扱いは「大規模差分時の Read 方針」参照）

未コミット変更（ワーキングツリー・ステージング）はレビュー対象外。未コミット変更をレビューしたい場合は、先にコミットしてから実行する。

自動生成ファイル（`**/*.d.ts` の OpenAPI 生成物、`bun.lock` 等のロックファイル、Prisma 生成物など）は指摘対象外とする。ただし「生成物差分が変更の意図と乖離していないか」は確認すること。

#### 変更ファイルを Read で全文取得する目的

- 差分の周辺文脈（呼び出し元・依存関係）をレビュー時に参照する
- メインセッション側での `.claude/rules/` 自動注入（`paths:` frontmatter による glob マッチ）を発動させ、後続の「適用ルールファイルの特定」を容易にする
- メイン側の Read による自動注入はサブエージェントのコンテキストには伝播しないため、サブエージェントが確実にルールを参照できるよう、共通フロー 2. で列挙したパス一覧を 3. でサブエージェントに渡す必要がある

#### 大規模差分時の Read 方針

変更ファイル数や差分行数が多くメイン側で全文 Read しきれない場合は、以下の優先順位で Read 対象を絞ってよい（**サブエージェントには差分全文は必ず渡す**。Read はメイン側で「適用ルールの特定」「対象ファイル一覧確定」を目的とするため）。

1. 差分が大きいファイル（`git diff --stat` 等で特定）
2. `.claude/rules/` の paths にマッチするファイル（ルール観点の確認のため）
3. 変更の中核となるビジネスロジックを含むファイル（`routes/`, `domain/` 等）

絞り込みを行った場合は、サブエージェントへの依頼メッセージに「Read 省略したファイル一覧」を明示し、サブエージェント側で必要に応じて Read させる。

### 適用ルールファイルの特定

`.claude/rules/` 配下の各ルールファイルは frontmatter に `paths:` glob を持ち、どのファイルパスに適用されるかを自己記述している。

- 対象ファイル一覧の各パスに対し、`.claude/rules/` 配下の全ルールファイルの `paths:` glob を照合し、マッチするルールファイルのパスを集合として列挙する
- 差分モードで 1 ファイルも変更がない場合、適用ルールは空でよい
- 1 ファイルに複数のルールが同時に該当した場合（例: `apps/frontend/src/routes/login.tsx` に `coding-style.md`・`typesafe-coding.md`・`jsdoc.md`・`writing-style.md` が全てマッチ）は、該当する全てのルールをサブエージェントに渡す。指摘の根拠としてはルール同士が被らない範囲でそれぞれ引用する（同一論点で重複引用は避ける）
- 列挙したパスは共通フロー 3. でサブエージェントへ渡す

例: 対象ファイル一覧が `apps/frontend/src/routes/login.tsx` と `apps/backend/src/routes/api/v1/file/router.ts` を含む場合、適用ルールは両ファイルとも `coding-style.md`・`typesafe-coding.md`・`jsdoc.md`・`writing-style.md`（TS/TSX にマッチ）。`.github/workflows/` の YAML には `github-actions.md` が適用される。

### レビュー範囲

- **差分モード（PR / ブランチ差分）**: 差分（変更された行）および変更の影響を受ける範囲のみを指摘対象とする
  - 対象: 変更行そのもの、変更箇所から呼び出される / を呼び出す範囲、変更により前提が崩れる未変更箇所、`docs/development/review-criteria.md` の「整合性」観点（変更と類似のパターンを持つ未変更コードへの修正漏れ等）
  - 対象外: 変更と無関係な既存コードの問題（変更前から存在する独立した不具合・スタイル違反等）
  - Read で取得した全文は、上記の判定と `.claude/rules/` 自動適用のためのコンテキストであり、**全文 = 指摘範囲ではない**
- **ファイル・ディレクトリモード**: 指定された対象の全内容を指摘対象とする

#### ファイル・ディレクトリを対象とする場合（パス指定）

差分ではなく、指定された対象の**現在の内容そのもの**をレビューする。既存コードの品質監査や、差分だけでは文脈が不足する場合に使う。

- 指定されたパスが存在することを確認する
- ディレクトリの場合は配下の全ファイルを対象とする（テストファイルを含む）。ユーザーが明示的に除外を指示した場合のみ除外する
- 対象ファイルの**全文**を取得する
