# レビュー結果の報告フォーマット

レビュー結果の出力仕様と具体例を定義する。

## 基本方針

- 指摘は重要度（🔴 高 / 🟡 中 / 🟢 低）で分類し、重要度ごとにセクションを分ける
- 重要度の判定基準:
  - 🔴 高: セキュリティ欠陥・仕様違反・重大な回帰・本番データへの影響・`.claude/rules/` 明示ルール違反の中で即修正が妥当なもの
  - 🟡 中: エラーハンドリング不足・テスト欠落・命名/構造の規約違反・新規で入ったコード重複など、マージ前に潰したい品質問題
  - 🟢 低: 整合性・スタイルの微妙なぶれ・将来リスク・情報補足
- 指摘番号 `#N` は**重要度セクションを横断して通し**で振る（🔴 の 1, 2 → 🟡 の 3, 4 → 🟢 の 5, 6 のように連続）
- 同一重要度セクション内での指摘と指摘の間には水平線 `---` を入れて視覚的な境界を明確にする
  - 以下の場所では水平線不要
    - セクション内での最初の指摘の前
    - セクション内での最後の指摘の後
- 各指摘は以下の3要素で構成する
  - **見出し**: `#{指摘番号} {簡潔なタイトル}`
  - **対象箇所**: バッククォートで囲んだ「ルートディレクトリ起点の相対パス + 行番号」を単独行で記載
    - 単一行の指摘: `path/to/file.ts:42`
    - 複数行にまたがる指摘: `path/to/file.ts:18-49`（開始行 + `-` + 終了行）。関数全体・ブロック全体など、問題範囲が単一行に収まらない場合に使う
    - ファイル単位の指摘: 行番号を省略し `path/to/file.ts`（ファイル全体の構造・存在そのものに関する指摘）
    - ディレクトリ単位の指摘: ディレクトリパス `path/to/dir/`（複数ファイルにまたがり、個別ファイルに落とせない指摘。例: 配置規約違反、命名の不統一）
    - 判定: 指摘が単一ファイルの改修で解決するならファイル単位、複数ファイルへの変更が必要ならディレクトリ単位
  - **詳細**: 指摘内容・根拠・推奨対応を自然文で記述。`.claude/rules/` のルールを根拠とする場合は、該当ルールファイルのパスを本文中で引用する
- 問題がない場合はその旨を簡潔に報告する
- レビュー対象が空（差分ゼロ、対象ファイルが存在しない等）の場合は「問題がない場合」と同じフォーマットで、**対象が空である事実と原因**を 1〜2 文で補足する

## 例: 指摘がある場合

```
【レビュー結果】

重要度: 🔴 高（2件）

#1 認証トークンの有効期限検証漏れ

`apps/backend/src/auth/verify.ts:42`

`verifyToken` は JWT のシグネチャのみを検証しており、`exp` クレームをチェックしていない。有効期限切れのトークンでも認証が通るため、流出トークンの悪用リスクがある。`jose.jwtVerify` のオプションで `currentDate` を渡すか、検証後に `exp` を明示的に比較する必要がある。

---

#2 SQL インジェクションの可能性

`apps/backend/src/accounts/search.ts:78`

検索クエリを文字列連結で構築している。ユーザー入力の `keyword` がそのまま SQL に埋め込まれるため、Prisma のパラメータバインディング（`$queryRaw` のテンプレートリテラル形式）に置き換えるべき。

重要度: 🟡 中（1件）

#3 エラーハンドリングで握りつぶしがある

`apps/backend/src/routes/api/v1/file/router.ts:25`

`catch` 節で `console.error` のみ実行しており、呼び出し元にエラーが伝播しない。UI 側で失敗状態を表示できないため、`throw` もしくは `Result` 型で返す形に変更する。

重要度: 🟢 低（1件）

#4 型定義の重複

`apps/backend/src/schema/file.ts`

`Schedule` 型と `ScheduleSummary` 型でフィールドの約 8 割が重複している。`Pick` / `Omit` で派生させると保守性が向上する。
```

## 例: 問題がない場合

対象の範囲や確認した観点などを簡潔に伝える。

```
【レビュー結果】

特筆すべき指摘はありません。`docs/development/review-criteria.md` の全観点で確認済み。
```

## 例: レビュー対象が空の場合

差分ゼロや対象ファイル不在など、レビューすべき対象そのものが存在しないケース。

```
【レビュー結果】

レビュー対象の差分は存在しません。`HEAD` は `origin/develop` と同一コミットを指しています。
```
