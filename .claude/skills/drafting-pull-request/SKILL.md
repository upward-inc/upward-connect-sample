# GitHub Pull Request の Draft 作成

現在チェックアウトしているブランチからプルリクエストを draft 状態で作成する。

## このスキルの位置付け

- 目的は PR 作成作業の負荷軽減であり、完成された PR 文を生成することではない
- 出力はあくまで draft であり、PR 作成者による手直しを前提とする
- ルールに従って一定の品質の叩き台を提供することにスコープを限定する。レビュアー視点での文章磨き込みや過度な意訳・補足は行わない

## 前提条件

- [GitHub CLI](https://cli.github.com/) がインストール・認証済みであること（`gh pr create` で PR を作成するため）
- Linear MCP サーバー（`linear-server`）が接続・認証済みであること（未接続でも skill は動作するが Issue を参照しない fallback になる）
- PR を作成するブランチがチェックアウトされていること
- リモートリポジトリにブランチがプッシュされていること

## 実行フロー

1. `git branch --show-current` で現在のブランチ名を取得
2. ブランチ名から Linear Issue ID を抽出する（例: `feature/uc-50` → `UC-50`）
3. `git fetch origin develop` でリモートの最新を取得
4. `git log --oneline origin/develop..HEAD` でベースブランチ（develop）からの差分コミットを確認
5. `git diff origin/develop...HEAD` で変更内容の詳細を確認
6. Linear Issue ID が抽出できた場合は Linear MCP の `mcp__linear-server__get_issue` ツールで Issue 本文を取得する（PR の主軸特定に使用する）
7. 変更内容を分析し PR を作成

```bash
gh pr create \
  --title "{title}" \
  --body "$(cat <<'EOF'
{body}
EOF
)" \
  --base develop \
  --draft
```

body は改行・バッククォート・日本語括弧を含む Markdown になるため、必ず上記の HEREDOC 形式（`<<'EOF'` のシングルクォート付き）で渡すこと。

## PR タイトル（title）の規則

- `{Linear Issue ID}: {簡潔な変更概要}` の形式を使う（例: `UC-50: 取引先検索に業種フィルターを追加する`）
  - Linear Issue ID が抽出できない場合は `{ブランチ名}: {簡潔な変更概要}` にフォールバックする
- `{簡潔な変更概要}` は diff とコミットログから最も中心的な変更を 1 行で表現する（付随的な test / refactor コミットは要約対象から外す）

## PR 説明（body）の規則

- `.github/PULL_REQUEST_TEMPLATE.md` を元に内容を入力する
- テンプレートの見出し行（`##` で始まる行）は一字一句変更しない
- テンプレート内の HTML コメント（`<!-- ... -->`）はそのまま残す
  - GitHub 上では非表示になるが、記述ガイドとして機能するため削除・エスケープしない
- 各セクションに該当内容がない場合は、テンプレート原文の空行・プレースホルダー（`- ` / `-` / 空行など、セクションごとに形状が異なる場合あり）をそのまま残す
  - 「なし」などの文言を書き加えない
  - プレースホルダー行自体を削除・編集しない
- 各セクションの入力ポリシー:
  - `変更の概要（Overview）`: 後述の「変更の概要（Overview）の記述ルール」に従う
  - `ローカル手動テスト内容（Manual Test）`: 後述の「ローカル手動テスト内容（Manual Test）の記述ルール」に従う
  - `補足（Supplement）`: レビュアーへの伝達事項がある場合のみ記述する
- 本文中で Linear Issue ID など、URL を伴わない短縮識別子を記載する場合は Markdown リンク形式で書く（例: `[UC-123](https://linear.app/upward-inc/issue/UC-123)`）
  - 識別子だけの記述はクリック可能なリンクにならないため、参照先へ辿れるよう明示的にリンク化する
  - URL をそのまま貼ること自体は問題ない
  - この形式は本文（body）のみに適用し、PR タイトルには適用しない（GitHub のタイトルは Markdown リンクを解釈しないため）

## 変更の概要（Overview）の記述ルール

`変更の概要（Overview）` セクションは以下の手順で記述する。

### 1. テーマの特定

PR の主軸（テーマ）を最初に決める。判定順位は以下のとおり。

1. Linear Issue を取得できた場合は、Issue で予定されていた内容を主軸とする
2. Linear Issue が取得できない場合は、コミットログのうち最も件数・行数の多いトピックを主軸とみなす

### 2. 変更の分類

各コミット・差分を以下のいずれかに分類する。判定軸は「関心領域 / レイヤー」が主軸と一致するか。

- **主軸に直結する変更**: テーマの目的を達成するための実装。主軸機能の単体テスト・主軸機能を利用するための既存コードの追従修正・主軸機能のドキュメント追記もここに含める
- **付随する変更**: 主軸と同じ関心領域・レイヤーで、主軸の作業中に発見・整理した変更（例: 主軸の機能で使うコンポーネントの軽微なバグ修正、主軸の作業中に抽出した共通フック・ユーティリティ）
- **無関係な変更**: 主軸と関心領域・レイヤーが異なる独立変更（例: 別画面のタイポ修正、別パッケージ・別レイヤー（frontend ⇔ backend）の改善）

判断に迷う場合は「主軸の PR から外しても主軸が成立するか」で考える。成立するなら付随または無関係、成立しないなら主軸に直結。

### 3. 記述の構造

- 主軸の意図と達成内容を 1〜2 文で先頭に置き、続けて主要変更を箇条書きで列挙する
- 同種の変更（同一機能の連続修正・同じファイル群への調整等）は 1 つの箇条書きに集約する
  - 粒度は「読み手が PR の輪郭を把握できる単位」を目安とする
  - 主軸の項目数は概ね 5 〜 10 程度に収める
- 各項目の本文は 1 文を目安に短く保つ
- 文末は「〜する」ではなく「〜した」（完了形）または「〜を追加」等の体言止めを使う（PR の時点で実装は完了しているため、現在形の動作記述より実態に合う）
- 補足情報（理由・例示・例外条件等）は子箇条書きに分けて構造化する
- 付随する変更がある場合は `### 付随する変更` セクションを設けて主軸と分離する
- 無関係な変更がある場合は `### 無関係な変更` セクションを設けて分離する
- 該当しないセクションは省略する（空セクションを残さない）

### 4. アンチパターン

- 「コミット 1 件 = 箇条書き 1 行」の機械的な対応にしない（diff の羅列ではなく、レビュアーが PR の意図を読み取れる粒度に統合する）
- 実装した順序どおりの動作手順として書かない。変更がもたらす結果・効果を主語にした概要として書く
  - NG（実装順の作業ログ。前の手順を受けて次を行う、という時系列の依存関係を書いてしまっている）:
    - schema に industry_code カラムを追加する
    - 追加した industry_code を使って検索 API に絞り込み条件を実装する
    - 実装した絞り込み条件に対応するフィルター UI を追加する
  - OK（各項目を独立した結果・効果として書く。前の項目への依存を語らない）:
    - 取引先データが業種を保持できるよう schema を拡張（した）
    - 検索 API に業種による絞り込みを追加（した）
    - 取引先検索画面に業種フィルターの UI を追加（した）

## ローカル手動テスト内容（Manual Test）の記述ルール

実装者が行うべき手動テスト手順を記述する。テストコードで担保されている場合は空のままにする

- 各項目は動作の説明文（「〜する」）ではなく、確認すべき状態を体言止め（「〜こと」）のテスト観点として書く（PR 作成時点は未実施の手順だが、Ready にする時点では実装者が実施済みとなることを見据えた表現にする）
- 文末のバリエーション: 「〜すること」（動作手順）／「〜であること」「〜ていること」（状態確認）／単純な「〜こと」の体言止め
  - NG（動作の説明文のまま止めている）:
    - フォームを送信する
    - 一覧画面に遷移することを確認する
  - OK（体言止めのテスト観点にする）:
    - フォームを送信すること
    - 一覧画面に遷移すること

## PR 記述言語の判定順位

1. コマンドの引数で指示を受けた言語（`$ARGUMENTS`）
2. `$LANG` 環境変数で確認可能な言語
3. `git config user.name` の直近のコミットメッセージから推測
4. 日本語（デフォルト）

## Linear Issue ID の抽出

- ブランチ名に含まれる `uc-{番号}` を抽出し、`UC-{番号}` を Linear Issue ID として扱う
  - 接頭辞（`feature/` / `bugfix/` / `hotfix/` 等）の形式には依存しない
  - 例: `feature/uc-50` / `hotfix/uc-50` / `uc-50` のいずれも `UC-{番号}` として認識する
