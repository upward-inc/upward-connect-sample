# Issue の起票

UPWARD Connect チームの Linear に Issue を起票する。

## 前提

- Linear MCP サーバー（`linear-server`）が接続・認証済みであること
- チーム識別子: `UC`
- Issue Type 選択の基準を定める Linear ドキュメントの slug: `issue-type-選択の基準-7fc724e9e02f`

## 実行フロー

1. 「テンプレート選択の基準」に従い `get_document` で選択基準を取得し、Issue 種別に最も適合するテンプレートを選ぶ
2. `list_templates`（team: チーム識別子, type: `issue`）で一覧を取得し、選んだ Type のテンプレートを `get_template` で取得する。`content.description` のセクション構成を下書きの骨格にする
3. `list_issue_labels` でラベル一覧を取得し、タイトル・説明文・ラベルを決定する（`Type` はテンプレートと1:1で対応するものを選ぶ。`Type` 以外は文脈に明確に合うものだけを付け、無ければ `Type` だけでよい）
4. 会話の文脈に参考リンクがあれば `links` フィールドに設定する。文脈に無いリンクは補わない
5. 下書きを「記述の原則」の各判定に照らして点検し、外れていれば直す
6. 下書きをユーザーに提示して確認を取る（ラベルは名前で表示する）
7. 承認後、`save_issue`（team: チーム識別子）で Issue を作成する。ラベルはステップ3で取得済みのラベルIDを渡す

いずれかの取得に失敗したらユーザーへ伝えて中断する。取得できなかった内容を推測で補わない。

## タイトルの規則

- 1 行で簡潔に
- 目的・現象を端的に表す（例: 「〜を追加する」「〜を改善する」「〜できない」「〜の脆弱性を修正する」）

## 記述の原則

何を書くかはこの節が定める。この節が置き場を名指しした内容は、そのセクションがテンプレートに無いときだけ、プレースホルダが決める。
下書きを作ったら、提示する前にこの節の「判定」で自己点検する。

### What には成立させたい状態を書き、実装手段を書かない

What に書くのは、完了時に何が成り立っているかと、実装が満たすべき制約。
どのファイルをどう変更するかは、実装者が決める余地として残す。

実装手段を書く場合は「実装案」へ置く。What から手段を外すことで、解くべき問題が説明の長さに埋もれない。
他の案を検討して退けたなら、その理由を添える。実装時に事情が変われば判断をやり直せる。

判定: What の各項目が、実装方法ではなく成立させたい状態になっているか。実装方法が混ざっていれば実装案（テンプレートに無いときは委ねた先）へ移す。

### 調査済みの知見は役割ごとに置き分ける

起票前に調査が済んでいる場合、得られた情報は捨てずに残す。置く場所で役割を区別する。

- 調査で判明した事実（計測値・原因・再現条件・現状の挙動）: Why
- 選定・検討した実装方法とその根拠: 実装案
- 実装方法の選定に至らない制約・注意点・未確定事項: 補足

判定: 調査で得た知見が、それぞれ上の役割どおりのセクション（そのセクションがテンプレートに無いときは委ねた先）にあるか。

### DoD にはこの Issue で新しく成立する条件だけを書く

型チェック・Lint・テスト・ビルドが通ることは書かない。
変更の内容によらず常に求められる条件であり、Issue ごとの差が出ないため、書いても情報が増えない。

例外は、その条件がこの Issue によって初めて成立する場合。
lint ルールの新設や CI ジョブの追加が当たる。
テストの追加は既存のジョブが自動で拾うため、「テストが通る」は新しく成立する条件にならない。
テストについて DoD に書くなら、「〜の振る舞いがテストで担保されている」のように担保される対象を述べる。

判定: その項目は、この Issue を実装しなくても既に成立しているか。成立しているなら DoD に書かない。

## 本文の記入

テンプレートのセクションは追加・削除・並べ替えをしない。取得した構成をそのまま使う。
記述の原則がプレースホルダに委ねた内容は、各セクションのプレースホルダが挙げている語と照らし、直接当たるセクションへ置く。語を上位概念へ広げて当てはめない。
直接当たるセクションが無ければ補足へ置く。

セクション名を見出しとして使い、プレースホルダ（`<...>`）の説明に従って内容を記入する。
文脈から埋められるセクションは積極的に埋め、書く情報が無いセクションは見出しだけ残す。
プレースホルダの文言自体は下書きに残さない。
プレースホルダ以外の本文（引用ブロック等）は、テンプレートの一部としてそのまま残す。

取得したテンプレートのセクション名には強調（`**`）が掛かっていることがある。
セクション名だけを使い、強調は持ち込まない。

記入時の形式ルール（文章スタイルは `.claude/rules/writing-style.md` に従う）：

- 長文の散文は避け、箇条書きとインデントで構造化する
  - 説明が並列にならないときだけ、セクションより下の見出しレベルで分ける
- チェックボックスリスト（`- [ ]`）は使わない
- ファイルパス・コマンド・コード識別子はインラインコード（バッククォート）で囲む
- Linear は本文中の Issue ID を「ID + タイトル」に展開するため、1 文に ID を連続・反復すると可読性が下がる。連続使用を避け、複数挙げるときは例えばバレットに逃すとよい
- 本文中で PR 番号など、URL を伴わない短縮識別子を記載する場合は Markdown リンク形式で書く（例: `[#589](https://github.com/upward-inc/upward-connect-internal/pull/589)`）
  - 識別子だけの記述はクリック可能なリンクにならないため、参照先へ辿れるよう明示的にリンク化する
  - URL をそのまま貼ること自体は問題ない

Issue ID の書き方（NG / OK）:

- NG（1 文に ID を連続・反復）: 「backend の設定追加は UC-123、設定 UI は UC-124 が担当する。UC-123 完了後に frontend 対応へ着手し、UC-124 と文言を揃える」
- OK（例: バレットに逃す）:
  - 各設定の担当:
    - UC-123（backend の設定追加）
    - UC-124（設定 UI）

## テンプレート選択の基準

Type は同名の Issue Template に 1:1 で対応するため、テンプレート選択は Type の選択基準で判定する。
その基準は Linear ドキュメント「Issue Type 選択の基準」を単一の情報源とし、インラインには定義しない。
スキル実行時に `get_document` で取得し、基準表と各境界の判定ルールに従ってテンプレートを選ぶ。
